Design note Final — thesis not supported 2026-07-29

I built the agent-query optimization thesis,
measured it, and it isn't there

Agents were supposed to flood warehouses with near-duplicate speculative queries — 10–20% distinct sub-plans, a large deduplication prize. I built the trace primitive to measure that, then measured it against real agents. Four versions of the claim, four failures. The tooling is real and useful; the prize is not.

The correction, first

The published measurement is precise: the BIRD text-to-SQL benchmark, 50 independent attempts per task, redundancy defined as “the proportion of distinct sub-expressions relative to total sub-expressions across multiple agent attempts.”

Every condition below differed on both axes — each agent got a different question, and I counted whole queries. So the conditions are real measurements of a neighbouring question, and were wrong to present as a refutation.

Both are true at once. Eight agents asked one question 55 different ways, but underneath scanned the same table with the same 13 predicates computing the same 10 measures. The repetition lives below the query, which is why counting queries could not see it — and why a query-keyed result cache, the thing every warehouse ships, captures almost none of it.

Everything in the sections that follow was measured correctly and concerns agents on different questions. It stands as its own result. It does not bear on the same-task claim, and the original framing of it as a refutation has been withdrawn.

Four versions of a different question

Speculation wasterefuted

The simulated agent used 4 of 93 results. Real agents used 34 of 41 across eight sessions — and that is verified against the answer text, not self-reported. One session of eight showed genuine waste (3 of 9 grounded). It is the exception, not the pattern.

Cross-session sharing13%, too small

The strongest reframe after the single-agent result: no agent need be wasteful, only for different people to ask related questions of the same tables. Deliberately overlapping questions, one warehouse, eight agents — 13%. Materialization still helps, but that is ordinary warehouse optimization, not an agent-specific prize.

Weak models fan outrefuted

The best theoretical argument, and the one the source paper implies most directly: if intelligence is free, you deploy small models at scale, and small models probe more. Haiku 4.5 on the identical question issued 5 queries to Opus's 6, with the same tight investigative structure. No fan-out.

The idle taxartifact of n=1

96.7% of a lone agent's bill was warehouse time spent waiting on the model — I published that as the one robust finding. With 8 concurrent agents sharing one warehouse, idle fell to 23.7%: 851 of 1116 billed seconds were productive. Their think-time gaps interleave. The measurement was right and the conclusion was wrong.

The finding that reversed itself

One agent · dedicated warehouse
2.9s productive 84s idle — 96.7%
Eight agents · shared warehouse
851s productive 265s idle — 23.7%

"You are paying a warehouse to watch an LLM think" is true of one agent on its own warehouse, and it is the kind of finding that is easy to publish and hard to un-publish. It disappears the moment agents share infrastructure — which is the only way anyone would actually deploy them. Measuring a single instance of a concurrent system produced exactly the wrong conclusion.

What survived: the trace primitive

What Postgres wrote to its own log
2026-07-28 23:41:07.882 PDT [16233] LOG: statement: /*agenttrace:t=673e90a1…,s=a17f2b,p=6c9e04,a=claude-code-analyst,c=refine,i=revenue%20by%20region*/ SELECT date_trunc('month', order_date), region, sum(amount) FROM orders GROUP BY 1, 2

Query lineage, per-agent cost attribution, and verified answer-grounding all reconstruct from a log the warehouse already writes, with nothing in the data path. Cost per resolved task — the number that decides whether an agent deployment survives budget review — becomes measurable where it wasn't before.

That is an observability tool. It is not an optimization platform, and the optimization code in the repo is now labelled as measured-and-small rather than built out further.

Verifying citations rather than trusting them

Whether a query's result reached the answer is the field the entire waste analysis rests on — and the obvious implementation, asking the agent, is the agent grading its own homework. So values from each result set are matched against the final answer with numeric tolerance for the rounding models do in prose ($319.9M for 319875432.11).

It catches errors in both directions. Haiku claimed three queries and was grounded in four — one it used but never claimed. Opus claimed six, all six grounded, five by a value no other query produced.

Five bugs, three of them flattering

Each of these moved a headline number. Three moved it in the direction I wanted, which is the part worth noticing.

Applied the simulator's 100× time dilation to a real trace The simulator compresses think-time; the scaling factor was applied unconditionally to timestamps that were already real. reported 2708s and 7 warehouse resumes → actually 27s and 1
Substring-matched numeric values Postgres returns numeric as a string, so result values were compared as text against prose. "69.33124…" never appears in an answer that says $69.33. grounding under-reported as 3/6 → actually 6/6
Regex-"parsed" SQL The extractor could not read GROUP BY 1, 2, date_trunc(), casts or aliases — precisely what real agents write — and emitted dimensions literally named "1" and "2". every covering-set number on real SQL was noise until it was replaced
Divided by the wrong denominator Counted queries the parser couldn't model as successfully deduplicated. reported 51% dedup → against servable queries, 20%
Line-anchored the citation regex Models write **CITED: q1, q4**; a /^CITED:/ scored that run as citing nothing. Haiku scored 0 claimed against 4 grounded

The parser replacement is the one that matters structurally. Its successor declines queries it cannot model — joins, CTEs, OR, HAVING — rather than guessing at them: 12 of 41 real queries excluded. Excluding lowers reported coverage; mis-parsing inflates it. Coverage figures here are lower bounds, deliberately.

What would still change my mind

  • A multi-agent coordinator spawning parallel subagents over one warehouse. This is the redundancy thesis's best remaining home and it is untested — concurrent investigators re-deriving each other's context is a different shape from eight independent sessions.
  • A wide schema — 100+ tables, where the agent must search for the right table before it can query it. Tool-surface confusion is where agents plausibly flail; two clean tables tests nothing.
  • Ambiguous, multi-cause questions. This dataset has one planted cause and a clean answer.

All three are a config change away in this harness, which is the actual deliverable. The negative result took eight agents and about six dollars of inference to produce; reviving the thesis would cost about the same.

The honest summary: a real trace primitive, a documented method for testing this class of claim cheaply, and a negative result that saves the next person a month. The optimization platform was not there to be built.
