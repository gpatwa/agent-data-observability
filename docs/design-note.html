Design note Revised after real-agent run 2026-07-28

Agent→data observability —
and the cost layer that mostly didn't survive contact

The trace primitive works: an agent's query plan tree reconstructs cleanly from warehouse logs with nothing in the data path. The optimization thesis built on top of it was then tested against a real agent, and two of its three findings did not reproduce. This is the honest version.

Two agents, one question

The same question — "why did revenue drop in July 2026?" — against the same 4.39M rows, traced identically. One agent is a simulator whose speculation shape was modelled on the published descriptions of agentic query fan-out. The other is Claude Opus 5 driving a single run_sql tool.

The real agent found the planted cause in seven queries — a per-order value collapse confined to EMEA × paid_search beginning 2026-07-12, with order volume flat — and correctly called it a pricing or currency bug rather than a demand problem. It wrote its own GROUP BY rollups instead of fanning out per-day probes, and cited every result it retrieved.

What held up, and what didn't

Speculation waste did not reproduce

The simulator spent 85% of its bill on queries whose results never reached the answer. The real agent's figure was zero — every result it fetched, it used. A capable model with a well-described tool does not flail the way the fan-out model assumes.

Synthesized anchors did not reproduce

This was the strongest technical idea here: the useful rollup is the query nobody ran. But all four of the real agent's covering anchors were observed queries — it had already written the rollups a materialization recommender would suggest. The recommender had nothing to recommend.

Redundancy weaker, and unreliable

Subsumption caught 90.3% of the simulated workload and 42.9% of the real one. Treat even that as soft: the shape extractor mishandles the positional GROUP BY 1, 2 and date_trunc() expressions real agents write, so the real-trace covering set is less trustworthy than the simulated one.

The idle tax reproduced

96.7% of the modelled bill was warehouse time spent waiting on the model rather than executing SQL. This is the finding that doesn't require agents to be wasteful — only slow between queries, which is intrinsic. But its magnitude collapses with the query count: batching saves 1.4×, not 7–9×, and the whole task costs seven cents.

Exact-match caching is worthless reproduced

Literal SQL matching caught 0% of the real workload and 1.1% of the simulated one; AST normalization added another 1–2%. Whatever value exists in this layer is in view-matching — not the prompt-level semantic caching today's LLM gateways ship.

n=1. One task, with one planted single-cause answer, one strong model, one good tool description. A vaguer question, a weaker model, or a harness that encourages parallel fan-out could look entirely different. Read this as "this agent, on this task, didn't speculate" — not as "agents don't speculate."

What still stands: the trace primitive

Two identical queries from two different user tasks are legitimately two queries. Two identical queries inside one agent's speculation loop are one query plus wasted spend. Same SQL, opposite verdicts — and nothing in a warehouse's query history distinguishes them.

So the chain runs in one direction only, and every link needs the one before it:

identity → plan lineage → redundancy classification → dedup / approximation → savings

Existing warehouse-cost tools start at step four, because steps one through three aren't recoverable from query history alone. That argument is unaffected by the results above — what the real run challenges is whether steps four and five are worth much once you have them.

The mechanism: stay out of the data path

Adoption dies at "install a proxy in front of your warehouse." So v1 adds nothing to the data path but a comment. Trace context is injected sqlcommenter-style; the warehouse logs it verbatim; the plan tree is reconstructed offline from a file the warehouse already writes. This worked unchanged for both the simulated and the real agent.

Values are URL-encoded, so quotes, spaces and */ in intent text cannot break out of the comment. Zero added latency, zero interception, nothing to trust.

Two fields can't come from the database at all. used_downstream needs the agent to record which results informed its answer. And on the real run, lineage itself is self-declared — the tool asks the model for intent and follows_from, so the tree is the agent's own account of its reasoning, with whatever inaccuracy that carries.

Where the money went — the one thing that held

Real agent · 27s wall clock · 1 warehouse resume
productive query execution — 2.9s idle + cold-start tax — 84s

The agent's think-time between queries is 1–9 seconds, so a 60-second auto-suspend never fires. The warehouse stays hot for the whole task while doing under three seconds of work. You are paying a warehouse to watch an LLM think — and that doesn't depend on the agent being wasteful, only on it being slow between queries, which is intrinsic to the architecture.

What the real run takes away is the magnitude. At seven queries the total is $0.073 and batching recovers 1.4×. The simulator's 7–9× came from having 93 queries scattered across a long window; that scatter was an artifact of the model, not an observed property of agents.

A bug worth naming. The first real-agent report claimed a 2708-second wall clock and seven warehouse resumes. The assembler was applying the simulator's 100× think-time dilation unconditionally to a trace whose timestamps were already real. Actual figures: 27 seconds, one resume. Dilation is now a CLI argument defaulting to 1 — the numbers on this page are post-fix.

The relative ordering survives — exact matching is near-useless, subsumption is where any value lives. What changes is the size of the prize, and how much you can trust the measurement. Tiers 2 and 3 use a tokenizer and a structured extractor for the common aggregate shape, not a real SQL parser. That was an acceptable shortcut for sizing a prize on synthetic SQL; it is not acceptable on the SQL a real agent writes, and the 42.9% should be treated as provisional until sqlglot or Calcite sits behind the same interface.

Trust ladder, revised

Each rung is still earned with evidence from the rung below. What changed is how much evidence rungs 3–5 now have behind them.

1
Observe validated on both agents

Comment injection, log reconstruction, fingerprinting, cost attribution. Read-only, out of path. The trace reconstructed cleanly from a real agent's traffic with no changes.

2
Advise weaker than modelled

Batching and warehouse-sizing recommendations. Still the best-supported intervention, but worth 1.4× on the real trace rather than 7–9×.

3
Materialize little evidence

Auto-create synthesized anchors. The real agent had already written its own rollups, leaving nothing to synthesize.

4
Intercept little evidence

Dedup, serve-from-anchor, approximate-first. Predicated on redundancy that a real agent did not exhibit.

5
Steer little evidence

Return guidance instead of data. Still unbuilt anywhere — but the case for needing it is weaker than it looked.

Where this leaves the idea

The observability primitive stands on its own. The trace reconstructs from logs the warehouse already writes, and cost per resolved task — the number that decides whether an agent deployment survives budget review — becomes measurable where it previously wasn't. Nothing in the real run undermines that.

The optimization layer is a different story. On this evidence the money is in scheduling and warehouse economics, not in deduplicating agent speculation. That is a narrower product than the one the simulation implied, and it sits closer to what the existing warehouse-cost vendors already do — which weakens the "they structurally can't copy this" argument that made the wedge attractive.

What could still change the picture

  • Harder questions. This one had a single planted cause and a clean answer. Ambiguous or multi-cause investigations may fan out far more.
  • Worse tool surfaces. The agent got one well-described tool over a clean schema. Real enterprise warehouses have thousands of tables and no such clarity.
  • Weaker or cheaper models. The economic argument for agents is that intelligence is cheap — which points at deploying smaller models at scale, and smaller models are exactly the ones expected to probe more.
  • Parallel fan-out harnesses. Multi-agent setups that spawn many concurrent investigators are the case the redundancy thesis was really written for, and this run didn't test one.

Each of those is a run, not an argument. The harness now exists — swapping the question, the model, or the tool surface is a one-line change, and the trace comes out the same shape every time. That is the actual deliverable.

Prototype: ~1,000 lines of Node against Postgres 18 with log_statement=all, 4.39M rows. Real agent is Claude Opus 5 driven headlessly through Claude Code, with the warehouse exposed as a single run_sql MCP tool; lineage is self-declared by the model via intent and follows_from. Warehouse pricing modelled on Snowflake XS, $3/credit, 60s minimum billing, 60s auto-suspend, applied to real Postgres execution times — treat the ratios as the finding, not the absolute dollars. Simulated-agent think-time is compressed 100× and scaled back before billing; the real agent's timestamps are used as-is. Source and raw run output: github.com/gpatwa/agent-data-observability.
