Agent→data observability, and the cost layer
that can only exist on top of it

Warehouse query logs can tell you what ran. They cannot tell you which reasoning step ran it — so “redundant” stays undefinable and every cost tool is guessing. This is the trace primitive that fixes that, plus measured results from a working prototype.

The dependency nobody has built through

Two identical queries from two different user tasks are legitimately two queries. Two identical queries inside one agent's speculation loop are one query plus wasted spend. Same SQL, opposite verdicts. Nothing in a warehouse's query history distinguishes them.

So the chain runs in one direction only, and every link needs the one before it:

identity → plan lineage → redundancy classification → dedup / approximation → savings

Existing warehouse-cost tools start at step four. That is why they optimize warehouses — sizing, auto-suspend, routing — rather than queries: steps one through three aren't recoverable from query history alone. Observability here isn't a go-to-market wedge that happens to come first. It's the technical precondition.

The mechanism: stay out of the data path

Adoption dies at “install a proxy in front of your warehouse.” So v1 adds nothing to the data path but a comment. Trace context is injected sqlcommenter-style; the warehouse logs it verbatim; the plan tree is reconstructed offline from a file the warehouse already writes.

Values are URL-encoded, so quotes, spaces and */ in intent text cannot break out of the comment. Zero added latency, zero interception, nothing to trust — and the same middleware seam is where phase 2 flips to in-path mode behind a config flag. The adoption story and the upgrade story reuse one component.

used_downstream is the exception: it can't come from the database at all. It needs the agent to record which results actually informed its final answer. That two-sided join is what turns “you ran 93 queries” into a number a budget owner reacts to.

Where the money went

productive query execution — 2.7s idle + cold-start tax — 430s

This is the finding I did not expect to be so lopsided, and it survived scrutiny: the agent's think-time between probes is only ever a few seconds, so a 60-second auto-suspend never fires. The warehouse stays hot for the entire 372-second task while doing 2.7 seconds of work. You are paying a warehouse to watch an LLM think.

The anchors are queries nobody ran

My first covering-set pass returned 68 anchors for 89 aggregate queries — useless. The bug was conceptual, not mechanical: it picked anchors from observed queries. But an agent that fires 31 per-day probes never issues the GROUP BY order_date rollup that would have answered all 31. Candidates have to be synthesized by lifting equality filters up into the grouping. After that, 9 anchors cover 85 of 89.

AnchorOriginCoversMeasured
select channel, order_date, region, count(*), sum(amount) from orders group by … synthesized 62732 rows · 318ms
select channel, region, sum(amount) from orders where order_date between … group by … observed 1612 rows · 174ms

The anchors were executed, not estimated: 764ms of anchor time against 2,712ms of probe execution — 71.8% less compute for the same answers. Three avg() retries are served from the anchor's sum + count rather than rescanning.

Why exact-match caching is worthless here

TierCatchesHit rate, this workload
exactliteral retries1.1%
ast_hashalias renames, predicate reordering, whitespace2.2%
subsumptionprobes answerable from a coarser result90.3%

Agents rarely repeat a query exactly. They probe around a region — one cell, then the neighbouring cell, then the same cut sliced by day. Semantic caching as shipped by today's LLM gateways operates on prompts and would catch essentially none of this. The prize is in view-matching and multi-query optimization: four decades of database literature that nobody has pointed at agent traffic.

Prototype honesty: tiers 2 and 3 use a tokenizer and a structured extractor for the common aggregate shape, not a real SQL parser. That's the right shortcut for sizing a prize; a product needs sqlglot or Calcite behind the same interface, and the hit rate will move.

Trust ladder

Each rung is earned with evidence produced by the rung below it. You never ask for write access before showing a number that hurts.

1
Observe prototyped

Comment injection, log reconstruction, fingerprinting, cost attribution. Read-only, out of path.

2
Advise next

Batch the probes into one warehouse window: $0.360 → $0.052 per task, 6.9×, with no query rewriting at all. Plus sizing and rollup recommendations.

3
Materialize later

Auto-create the synthesized anchors and route the semantic layer at them.

4
Intercept later

Middleware flips in-path: dedup, serve-from-anchor, approximate-first with exact-on-final.

5
Steer later

Return guidance to the agent instead of data — “that's a 2TB scan, here's the rollup.” No commercial implementations exist today.

What could sink it

  • The measurement is the easy half. used_downstream needs per-framework agent hooks. It's the highest-value field and the most likely to slip.
  • Subsumption checking must cost less than the query it saves. Cheap AST hashing inline, expensive cover computation offline — or it's a science project.
  • You're building a high-volume telemetry system to reduce a data bill. Your own storage economics need to be good, or the irony becomes the sales objection.
  • Snowflake ships native attribution and the wedge evaporates. They bought Natoma in May 2026 and shipped the Cortex AI Gateway this month; they are actively claiming this layer. Being cross-warehouse from day one is the only durable answer — the multi-engine shop can't use vendor-native tooling.
  • Timing. Rungs 3–5 need agent workloads at real scale. If enterprise deployment stalls in pilots, the optimizer has nothing to optimize.

Prototype: ~700 lines of Node against Postgres 18 with log_statement=all. Warehouse pricing modelled on Snowflake XS, $3/credit, 60s minimum billing, 60s auto-suspend. Agent think-time is compressed 100× in the simulation and scaled back before billing; query execution time is real and never scaled. Per-task dollar figures come from one XS warehouse and one trace — treat the ratios as the finding, not the absolute numbers.
