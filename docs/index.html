Measurement report Negative result July 2026

The duplicate-query problem is real.
It just isn't the agents.

The prediction was that AI agents fire thousands of near-identical speculative queries — only 10–20% of their sub-plans distinct — leaving a large deduplication prize. I built the tracing to measure it and ran six conditions designed to give the claim its best shot. Agents came in at 0–43%. Then I scored 18.9M queries from real Redshift production fleets on the same metric: 91.3%. The prize exists. It belongs to the dashboards and pipelines already running, not to the agents.

The two conditions closest to the thesis's own premise produced the least redundancy of anything tested. A coordinator delegating to parallel subagents — independent investigators with no shared context, the exact shape the argument describes — came in at 9.1%, the lowest in the set, with every one of its 25 results used in the final answer. Delegation bought more distinct work, not duplicated work.

Six versions of the claim

  • Agents waste most queries on speculation. Real agents used 34 of 41 results across eight sessions — verified against the answer text, not self-reported.
  • Cross-session sharing is where redundancy lives. Eight agents on deliberately overlapping questions: 13%. Three of 23 per-session rollups eliminated.
  • Weak models fan out — and "intelligence is free" implies small models at scale. Haiku 4.5 issued 5 queries to Opus's 6.
  • You're paying a warehouse to watch an LLM think. True at 96.7% for a lone agent — but 23.7% once eight agents share one warehouse. Their think-time gaps interleave.
  • A coordinator will duplicate its subagents' work. 9.1%, the lowest measured.
  • A wide schema makes agents flail. Query count nearly tripled (6→17) — but the extra traffic was information_schema discovery, which no rollup can serve. Redundancy among servable queries was unchanged.

What survived: the measurement itself

Trace context rides into the warehouse as a SQL comment. The warehouse logs it verbatim, and the agent's whole plan tree is reconstructed offline — nothing sits in the data path, nothing to trust, no latency added.

LOG: statement: /*agenttrace:t=673e90a1…,s=a17f2b,p=6c9e04,a=analyst,c=refine,i=revenue%20by%20region*/ SELECT date_trunc('month', order_date), region, sum(amount) FROM orders GROUP BY 1, 2

That yields per-agent query lineage, cost per resolved task, and — the part that mattered most here — verified answer-grounding. Whether a query's result reached the answer is the field the entire waste analysis rests on, and asking the agent is the agent grading its own homework. So values from each result set are matched against the answer text with numeric tolerance for the rounding models do in prose. It caught errors both ways: one agent claimed three queries and had used four; another claimed six and had used six.

This is an observability tool, not an optimization platform. The optimizer in the repo is measured, small, and deliberately not built out further.

Six bugs, four of them flattering

Each moved a headline number. Four moved it toward the result I wanted, which is the part worth knowing before you trust any of the above.

Named the subagent tool Task instead of Agent The coordinator condition ran with delegation silently disabled. An unknown tool name doesn't error — the model just never delegates, and the trace looks like a perfectly valid single-agent run. an entire experimental condition was invalid and had to be rerun
Regex-"parsed" SQL The extractor couldn't read GROUP BY 1, 2, date_trunc(), casts or aliases — exactly what real agents write — and emitted dimensions literally named "1" and "2". every redundancy number on real SQL was noise until it was replaced
Divided by the wrong denominator Counted queries the parser couldn't model as successfully deduplicated. reported 51% dedup → against servable queries, 20%
Applied a simulator's 100× time dilation to a real trace Scaling meant for compressed think-time was applied to timestamps that were already real. reported a 2708s task with 7 warehouse resumes → actually 27s and 1
Substring-matched numeric values Postgres returns numeric as a string, so results were compared as text against prose. "69.33124…" never appears in an answer that says $69.33. grounding under-reported as 3/6 → actually 6/6
Line-anchored the citation regex Models write **CITED: q1, q4**; a /^CITED:/ scored that run as citing nothing. one model scored 0 claimed against 4 grounded

What this isn't

  • Not a study. One dataset, two models, six conditions, one run each. A cheap screen, run before building — which is the point.
  • Every dataset had a single planted cause. Genuinely ambiguous, multi-cause questions are untested and are the most promising remaining condition.
  • Coverage figures are lower bounds. The parser declines queries it can't model — joins, CTEs, OR, HAVING — rather than guessing at them. Excluding lowers reported coverage; mis-parsing would inflate it.
  • Costs model Snowflake, run on Postgres. Snowflake XS billing applied to real Postgres execution times. The ratios are the finding, not the dollars.
